## 状态规则

- 每项任务当前状态只能是 `TODO`、`待验证` 或 `DONE`；新任务一律从 `TODO` 开始。
- 实现已完成但仍待验证或验收的任务标记为 `待验证`。
- 只有 Derek0120 明确确认该项验收完成后，才能将状态改为 `DONE`。
- 代码提交、PR 合并或 CI 成功都不代表用户确认；不得自动将任务标为 `DONE`。
- 有待确认的产品/运维决策时，先记录选择并取得确认，再开始受其影响的任务。

### Dart 功能测试覆盖要求

- Dart/Flutter 测试须覆盖 [功能需求](design.md) 和 [业务规则](淮安80分业务规则.md) 中的每个功能点；不得只覆盖 UI 原型交付物。
- 为每个需求点建立可追溯的测试映射（文档章节到 Dart 测试），并随对应任务新增或更新测试；文档新增或修改功能点时，同步调整映射和测试。
- 业务规则的权威实现仍由服务端 Go 规则测试验证；Dart/Flutter 测试覆盖每项规则对应的客户端输入、交互、状态和展示行为，不将客户端测试当作服务端规则验证的替代。
- UI 交互测试应覆盖主要成功、失败和边界状态。Flutter 界面和依赖 Flutter 的功能测试使用 `flutter test`；纯 Dart 测试可使用 `dart test`。

### Dart / Flutter 测试工具约定

- `dart analyze` 和 `dart test` 都需要可用的 Dart SDK；没有 Flutter 并不自动意味着系统也没有 Dart，但本仓库当前 runner 未安装 `dart`，因此无法在该环境验证这些命令。
- `dart analyze` 可用于纯 Dart 源码；本项目客户端依赖 Flutter SDK（`package:flutter`、`flutter_test`），独立 Dart SDK 无法替代 Flutter SDK 来解析和测试 Flutter 界面。
- `dart test` 运行的是 `package:test` 测试；客户端当前未声明该依赖。纯 Dart 单元测试可以单独采用该方式，但 Flutter widget/界面测试必须使用 Flutter SDK 和 `flutter test`。客户端分析建议使用 `flutter analyze`。
- Flutter SDK 暂不可用时，Dart-only 测试只有在单独安装 Dart SDK、配置纯 Dart 依赖且测试不依赖 Flutter 包的情况下才可运行；UI 和 Flutter 功能测试由 Derek0120 本地使用 Flutter SDK 执行。

## 已确认选择（T01）

以下选择会影响构建或发布，已按默认方案确定：

1. **iOS 打包**：暂不提供 iOS 打包 Action；如后续需要，须另行确认签名材料及分发方式。
2. **Windows MSIX 签名/分发**：使用 msix 工具默认的开发签名配置；正式分发前配置可信签名证书或 Microsoft Store 流程。自签名包的接收方需信任对应证书才能安装。
3. **服务端分发方式**：仅生成 Docker 镜像归档并上传至 GitHub Actions run，不自动推送到镜像仓库。
4. **架构文档第 13 节**：采用其中记录的默认决策；生产容量、备份及 RPO/RTO 数值在生产发布前明确，Web 插件与浏览器范围在技术验证中确定。

## 当前构建工作流约定

应用源码位于 `server/`（含 `go.mod`、`cmd/server` 和 `Dockerfile`）及 `client/`（Flutter 共享客户端）。工作流约定 master 上的服务端代码变更构建 Linux/amd64 Docker 镜像归档；客户端代码变更构建 Windows MSIX。暂不提供 iOS 打包 Action。产物上传到对应 GitHub Actions run，不自动发布到商店或镜像仓库；MSIX 当前使用开发签名，正式分发前需配置经确认的签名证书或商店发布流程。
